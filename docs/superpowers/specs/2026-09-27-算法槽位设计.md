## 一、为什么要有这份规范

平台在算法接入上已经踩过三次坑，根因都是**同一个**：槽位职责没定义清楚。

| 时间 | 事件 | 根因 |
|------|------|------|
| 2026-05-14 | 原始设计只有**一个**算法入口，输出三分类（阳性/阴性/质量不佳） | 没有槽位概念，所有职责压在一个函数里 |
| 2026-09-26 | 为两人分工引入 A/B：检测=**病灶定位**、分类=**诊断三分类** | 名称与职责仍未被正式定义 |
| 2026-09-27 | 接入队友模型后出现「**任何图都显示阳性**」 | 队友模型输出的是**预后**（灌肠复位成功/失败），契约却要求**诊断**（阳性/阴性）→ 只能填占位值 |
| 2026-09-27 | 平台方（我）一度用预后成功率反推诊断，被回退 | 同一个混用错误，方向相反 |

**结论**：先用一份规范把「每个槽位回答什么问题、输出什么字段」固定下来，再动手改代码。

## 二、槽位定义（已确认）

平台对外只有**两个**算法槽位，名称统一为「**检测**」和「**预后**」：

| # | 槽位 | 一句话职责 | 输入 | 输出 | 当前状态 |
|:--:|------|------|------|------|------|
| 1 | **检测** | **识图 + 判辨阴阳性** | 医学影像文件 | 阴阳性（**二分类**）、诊断置信度、病灶框、标注图 | ⏳ **本地还没有** |
| 2 | **预后** | **预测治疗结局** | 医学影像文件 | 成功率、严重程度、处置建议 | ✅ 现成（YOLO 切面 + 横纵切 5 折集成 + ResNet18） |

> 旧称「分类」作为**槽位名**作废。凡是指槽位的地方，一律写「检测」「预后」。

### 2.1 预后槽位的内部逻辑（已确认）

```
影像
  │
  ▼
① 切面分类（横切 hengqie / 纵切 zongqie）      ← cut_best.pt
  │
  ├─ 横切 ─→ 横切 5 折模型集成 ─┐
  └─ 纵切 ─→ 纵切 5 折模型集成 ─┤
                                ├─→ 融合 → 治疗成功率 → 严重度、处置建议
        ResNet18 ───────────────┘
```

即：**先判横/纵切面，再用该切面对应的模型预测成功率**，与 ResNet18 融合。
切面分类是预后的**内部步骤**，不对外单独出字段。

### 2.2 边界（不做什么）

| 槽位 | ✅ 负责 | ❌ 不负责 |
|------|------|------|
| 检测 | 识图、判定阴阳性、定位病灶并画框/出标注图 | 不预测治疗结局（不输出成功率、严重度、建议） |
| 预后 | 切面分类、预测成功率、给严重度与处置建议 | **不改变诊断结论**（不得改写阴阳性） |

> ⚠️ **铁律一**：阴阳性（`classification`）只能由**检测**槽位产生。
> 预后槽位输出的任何数字，**不得**用于推断阴阳性。
> （依据：「灌肠复位成功」的前提是「已确诊肠套叠」，拿预后反推诊断没有临床依据。）

### 2.3 字段归属表（本规范的核心）

| 结果字段 | 含义 | 归哪个槽位 | 缺省行为 |
|------|------|:--:|------|
| `classification` | 诊断结论：`肠套叠阳性` / `肠套叠阴性` | **检测** | 必填，**不允许占位**（见 §5） |
| `confidence` | **诊断**置信度（0~1） | **检测** | 必填 |
| `class_probabilities` | 阴阳性二分类概率 | **检测** | 可选 |
| `roi_box` | 病灶框 `(x1,y1,x2,y2)` 原图坐标 | **检测** | 可选 |
| `result_image` | 带病灶框的标注图 | **检测** | 可选 |
| `detection_score` | 检测环节自身置信度 | **检测** | 可选 |
| `treatment_success_rate` | 治疗成功率（0~1） | **预后** | 可选；仅阳性有意义 |
| `severity` | 严重程度：轻/中/重度 | **预后** | 可选；仅阳性有意义 |
| `treatment_advice` | 处置建议文本 | **预后** | 可选；缺失时平台按诊断结论给默认文本 |
| `detection_model_*` | 检测槽位的模型名/版本/耗时 | **检测** | 留空则前端不显示该行 |
| `prognosis_model_*` | 预后槽位的模型名/版本/耗时 | **预后** | 同上 |

> 🔧 **本次结构改动**：字段名与槽位名对齐 ——
> 保留 `prognosis_model_name / prognosis_model_version / prognosis_ms`（表示预后槽位），
> **`classification_model_*` 停止作为"槽位"字段使用**（DB 列保留不删，避免动历史数据；
> 但不再写入，历史值需重跑一次迁移到新结构）。

## 三、数据流与调用关系

```
影像文件
   │
   ▼
┌──────────── 槽位 1：检测（识图 + 判阴阳性）────────────┐
│  识图 → 阴阳性二分类 + 诊断置信度                       │
│  〔可选〕定位病灶 → roi_box、标注图                      │
└──────────────────────┬────────────────────────────────┘
                       │
        阴性 ──────────┴────────── 阳性
         │                          │
    是否继续跑预后？          ▼
    （见 §6 Q2）   ┌──── 槽位 2：预后（预测治疗结局）────┐
                   │  切面分类 → 对应模型 → 成功率        │
                   │  → 严重度 → 处置建议                 │
                   │  ⚠️ 不得改写阴阳性                    │
                   └──────────────────────────────────────┘
```

**平台侧唯一入口不变**：`algorithm.pipeline.detect_intussusception(image_path) -> DetectionResult`
（平台只依赖这一个函数，槽位内部如何拆分由算法侧决定。）

## 四、契约

### 4.1 槽位 1 契约（检测）

```python
def detect_intussusception(image_path: Path) -> DetectionResult   # 只填诊断相关字段
```

| 字段 | 必填 | 说明 |
|------|:--:|------|
| `classification` | ✅ | **二分类**：`肠套叠阳性` / `肠套叠阴性` |
| `confidence` | ✅ | 诊断置信度 0~1 |
| `class_probabilities` |  | `{"肠套叠阳性": 0.9, "肠套叠阴性": 0.1}` |
| `roi_box` |  | 病灶框 `(x1,y1,x2,y2)` |
| `result_image` |  | bytes / 文件路径 / ndarray |
| `detection_score` |  | 检测环节置信度 |

### 4.2 槽位 2 契约（预后）

```python
def classify_prognosis(image_path: Path) -> PrognosisOutcome
```

| 字段 | 必填 | 说明 |
|------|:--:|------|
| `treatment_success_rate` |  | 0~1；仅阳性有意义 |
| `severity` |  | `轻度` / `中度` / `重度` |
| `treatment_advice` |  | 处置建议文本 |
| `view` |  | 可选：内部判定的切面（横/纵），用于排查，不单独展示 |
| `method_detail` |  | 可选：各子模型明细（切面模型的概率、5 折各自成功率、ResNet 成功率） |

两个槽位各自在自己的代码里声明 `NAME` / `VERSION`，平台自动填入
`detection_model_*` / `prognosis_model_*`。

## 五、规范条款（必须遵守）

1. **禁止占位**：`classification` 必须来自真实的诊断判断。检测模型未就绪时，
   平台走 Mock（`model_name="Mock"`）并在界面标注"演示数据"，**不得**用预后结果或字面量冒充诊断。
2. **禁止跨槽位推断**：预后槽位不得修改或推断阴阳性。
3. **模型名必填**：交付时 `NAME` / `VERSION` 必须填真实值，不允许留 `TODO` 字样。
4. **可选字段缺失不算错**：缺失的可选字段由平台补默认值；必填字段缺失会让整次检测失败。
5. **单次检测只落一条结果**：同张影像重复检测覆盖旧结果（保持一致）。
6. **两个槽位互相独立**：任一槽位未就绪时，另一个仍可正常工作（检测缺 → 仍可出预后；
   预后缺 → 只出诊断结论），平台按"哪个槽位空着就不显示那一行"渲染。
7. **报告可追溯且不混淆**：结果页与打印报告必须写明两个槽位的模型名与版本；
   「诊断结论」与「治疗成功率」必须分开标注，不得混称"置信度"。

## 十一、⚠️ 上线阻塞项：检测模型的域外误报与置信度饱和（2026-09-27 实测）

检测槽位（`intussusception-obb` v1.0.0，部署阈值 `0.014451`）接入后，用平台真实入口实测发现两个**阻塞上线**的问题。

### 11.1 非医学图像被判「肠套叠阳性」，且置信度很高

| 输入（**都不是超声图**） | 判定 | 显示置信度 | 证据分 |
|---|---|---|---|
| 随机噪声（seed=0） | **肠套叠阳性** | 98.27% | 0.2587 |
| 随机噪声（seed=1） | **肠套叠阳性** | 98.27% | 0.1847 |
| 随机噪声（seed=2） | **肠套叠阳性** | 98.27% | 0.2139 |
| 随机噪声（seed=42） | **肠套叠阳性** | 98.27% | 0.2716 |
| 随机噪声（seed=123） | **肠套叠阳性** | 98.32% | 0.3609 |
| 随机噪声（seed=777） | **肠套叠阳性** | 98.27% | 0.1996 |
| 灰色渐变 | 肠套叠阳性 | 96.67% | 0.1060 |
| 医院 Logo | 肠套叠阳性 | 94.86% | 0.0147 |
| 纯黑图 | 图像质量不佳 ✓ | 90% | 0.0000 |
| 纯白图 | 肠套叠阴性 ✓ | 94.89% | 0.0000 |

**6/6 个不同种子的纯噪声全部被判阳性**，不是个别样本的偶然。

**根因**：部署阈值 `0.014451` 远低于"有结构的图像"能拿到的分数。真实超声影像的证据分是 0.757~0.909，噪声是 0.18~0.36 —— 分数其实分得开，但阈值定在 0.0145，等于放行一切有结构的图。安全网只拦"接近全黑的暗帧"，拦不住噪声/示意图/Logo。

### 11.2 显示"置信度"对真实阳性没有任何区分度

10 张真实超声影像的证据分 **0.7569 ~ 0.9087（彼此不同）**，但显示置信度**全部是 0.9923**。

原因在标定表 `model_core.CALIB_POS`：分数 ≥ 0.75 后一律映射为 0.9923（表里 0.75 / 0.9 / 1.0 三个锚点同值）。

而且这个数字的语义不是"这个病人阳性的概率"，他们自己在 `model_core.describe()` 里写明是：

```
"confidence_semantics": "阳性:P(阳性|证据分>=s)；阴性:P(阴性|证据分<=s)"
```

即**该分数区间上的历史精度**（precision at score），且建立在一个他们自己承认有来源混淆的评估集上（见其接入说明 §9.4）→ 该精度是**上界**。

**结论**：`confidence` 既无区分度、语义也不是医生理解的"置信度"。前端把它标为"置信度"会误导。

### 11.3 处理建议（按顺序）

1. **补域外/质量门控**：非超声特征（无灰阶包络、无扇形/矩形扫描区、饱和度异常等）不应进入筛查判定，应给「图像质量不佳」。
2. **重标阈值**：需要用**无偏的阴性样本**重新标定。我的实测显示阈值抬到 ~0.5 可把上述域外样本全部排除，同时仍把 10 张真实影像判为阳性 —— 但这只是 **n=10 的观察，不是标定**：平台数据里**一例真实阴性都没有**，这个数据缺口必须先补上。
3. **改展示语义**：把 UI 上的「置信度」改为「证据分 / 模型参考精度」或同时展示原始证据分，避免医生把 99.23% 读成"确诊把握 99%"。

> 📌 **数据缺口（需要与临床/队友协调）**：要同时解决 11.1 和 11.2，必须有**真实阴性病例**与**非目标图像**作为验证集；当前 19 张影像全部是阳性样本，无法验证假阴性风险。
