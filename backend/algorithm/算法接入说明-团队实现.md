## 2. 契约映射（我们的模型怎么落进"检测 + 分类"）

本项目的模型是**联合的 OBB 检测+分类模型**（YOLO-OBB 双模型委员会），输出只有一个连续"证据分"和一个病灶框，
不是可以干净拆开的两个阶段。按契约允许的方式映射：

```
detection.detect(image)
    └─ 完整跑一遍委员会推理 → score（证据分）+ 最佳病灶框
    └─ 返回 ROI(image=原图, box=框|None, score=证据分)
         · 故意**不裁剪 ROI**：本项目模型对"取景"高度敏感（病灶占画面比例是关键变量），
           裁掉上下文会改变判定；契约明确允许"全图送分类"（ROI(image=原图)）
         · 把 score 放在 ROI 上，是为了让分类模块**复用**同一份推理结果 ——
           否则每个请求跑两遍模型，而本项目绝大多数阴性样本的 score 恰好为 0，正是最易重复推理的那类

classification.classify(roi)
    └─ 优先复用 roi.score（不再推理）；score 缺失时才自己跑一遍
    └─ 按阈值 + 安全网判成三分类之一
```

→ **一次请求只跑一遍模型**。

### 2.1 双模型溯源（`detection_model_*` / `classification_model_*`）

平台新增了 A/B 双模型溯源：`pipeline.py` 读取两个子模块的 `NAME` / `VERSION` 常量。本项目的填法是：

| 侧 | 模块 | `NAME` | `VERSION` |
|---|---|---|---|
| 检测 A | `detection/__init__.py` | `intussusception-obb-detector` | `1.0.0` |
| 分类 B | `classification/__init__.py` | `intussusception-obb-decider` | `1.0.0` |

> 本项目是**联合的 OBB 检测+分类模型**：检测侧负责跑委员会拿到证据分与病灶框；
> 分类侧负责阈值判定 + 概率标定 + 安全网。因此拆成这两个名字，而不是虚构两个独立网络。
> 名字里**不含**实验代号、随机种子、训练配方等内部信息（避免泄露训练细节）。

### 2.2 病灶框标注图（`ROI.annotated_image`）

平台新增「原图 / AI 标注图」切换与打印报告优先使用标注图。本实现：

* **阳性**：把病灶 OBB 四角点画成红色多边形 + 顶部状态条「AI 检出疑似病灶 证据分 x.xxx」；
* **阴性 / 图像质量不佳**：**不画框**（避免在阴性结果上画框造成误导），只加状态条「AI 未检出明确病灶 证据分 x.xxx」；
* 形态用 **JPEG 字节**（契约推荐，平台侧零依赖）；编码失败返回 `None`，**绝不影响诊断结果**；
* **始终提供**这张派生图：平台在 DICOM 输入下默认展示标注图，恒定提供可避免 DICOM 原图显示异常。

同时，`roi_box` **只在判定为阳性时给出**（检测阶段即按阈值门控）——否则阴性结果也会带一个病灶框。
实测标注图体积：768×576 → 85 KB（标注图会增加约 30 ms 的编码开销，端到端仍在 1.0–2.5 s）。

### 2.2.1 病灶框的旋转信息：`ROI.polygon` / `roi_polygon`（本次新增）

`roi_box` 是 `(x1,y1,x2,y2)`，即旋转框的**外接矩形** —— 会把 OBB 的旋转信息丢掉。
模型输出的本来就是旋转框，压成外接矩形后框必然变大，实测代价很大：

| 数据 | R@IoU 0.30 | R@IoU 0.50 | R@IoU 0.75 |
|---|---|---|---|
| 语料 800 张：保留 OBB | 98.0% | 93.6% | **66.9%** |
| 语料 800 张：只留外接矩形 | 98.0% | 92.2% | **55.9%** |
| test190 190 张：保留 OBB | 96.3% | 90.5% | **71.1%** |
| test190 190 张：只留外接矩形 | 95.3% | 91.1% | **60.5%** |

⇒ **R@IoU 0.75 白掉 10.5~11.0pp，两批独立数据一致**。
按 GT 框旋转角分层可见，连 GT 完全轴对齐（<2°）的样本也损失 8.0pp ——
因为损失来自**模型自己的旋转输出被压平**，与 GT 有没有旋转无关。

因此新增 **`roi_polygon`**：旋转框四角点 `(x1,y1,x2,y2,x3,y3,x4,y4)`，原图像素坐标。

* `algorithm/contracts.py`：`ROI.polygon`
* `algorithm/detection/__init__.py`：阳性时填入真实四角点（`roi_box` 保持不变，仅作兼容）
* `algorithm/pipeline.py` → `algorithm/interface.py`：`DetectionResult.roi_polygon` + `_clean_polygon`（必须恰好 8 个数）
* 平台侧：`models.py` / `schemas.py` / `services/detection.py` 各加一处，`main.py` 的 `ensure_columns` 自动为旧库补列
* **`roi_box` 一字未改**，既有断言与前端叠加逻辑全部继续可用

> 注意：**不能把 8 个坐标塞进 `roi_box`** —— `_clean_box` 恰好解包 4 个值，传 8 个会抛错并**静默丢弃整个框**。
> 下游（入库 / 前端画框 / 按框算指标）应**优先用 `roi_polygon`**，`roi_box` 只作回退。

### 2.2.2 病灶框的来源：只取紧凑档成员（`box_source="compact"`）

委员会原先跨「large + compact 两个成员 × 640/1280 两个尺度」取**置信度最高**的框。
实测这个规则会挑中 large 档的框，而 large 档的框明显更差：

| 选框来源 | R@IoU 0.30 | R@IoU 0.50 | R@IoU 0.75 |
|---|---|---|---|
| 委员会取最高分（旧） | 96.3% | 91.6% | 72.1% |
| **只用 compact 成员（新）** | 96.3% | **93.7%** | **74.2%** |
| 只用 large 成员 | 94.7% | 88.4% | 63.7% |

因此在 `POLICIES["v1"]` / `["v1r"]` 中加入 `"box_source": "compact"`
（`"committee"` 可一键回退）。**判定口径完全不变，只换框来源**，故 Precision / Accuracy / Sensitivity 不受影响。

### 2.3 DICOM（`.dcm`）支持情况

算法侧**支持 DICOM**（`pipeline.load_image` 用 pydicom 解析像素，`model_core` 负责转 BGR）。
以下均为实测结果（构造各类变体走平台同一条入口），输入影像为一张已知阳性帧：

| DICOM 变体 | 结果 |
|---|---|
| 8 位 / 16 位 MONOCHROME2 | ✅ 阳性 0.9923 |
| 隐式 VR 小端 | ✅ |
| 带 RescaleSlope/Intercept | ✅（16 位 min-max 归一化会抵消线性 rescale） |
| **多帧 cine（`(frames,H,W)`）** | ✅ 均匀抽 ≤3 帧逐帧打分，**取最佳帧**（修前会被判「图像质量不佳」） |
| **RLE 无损压缩** | ✅ pydicom 原生解码 |
| **JPEG Baseline** | ✅ 经 Pillow 插件解码 |
| **JPEG2000 无损** | ✅ 经 Pillow 插件解码 |
| JPEG-LS | ⚠️ 未验证（需额外解码器，如 `pyjpegls` / `gdcm`） |
| **MONOCHROME1（反相）** | ⚠️ **未处理**：`pipeline.load_image` 只回传 `pixel_array`，丢失了 PhotometricInterpretation，算法侧无从得知需要反相。超声几乎都是 MONOCHROME2，风险低；若要覆盖，需平台在 `load_image` 里一并回传该标签，或按 MONOCHROME1 预反相。 |

**已知的平台侧问题（已修，请审阅）**：`routers/images.py` 原先**先按客户端声明的 `content_type` 拦截**，
而浏览器选中 `.dcm` 时 `File.type` 常为空串 → multipart 该部分没有 Content-Type → `file.content_type` 为 `None`
→ 返回 `400 Unsupported type: None`；声明成 `application/octet-stream` 同样被拒。
平台自己写了字节嗅探（`_sniff_image_type`）正是为了不信任客户端声明，却先被声明卡住。
已改为**以嗅探结果为准**：`声明类型或嗅探类型任一在允许清单内即放行`，并保留"普通图片声明与内容必须一致"的校验。
实测：无 Content-Type / `application/octet-stream` / `application/dicom` 三种情形均 200；
真 PNG 谎报 jpeg 仍 400、随机字节仍 400，安全性未削弱。

### 2.4 图像格式支持矩阵（JPG / PNG / BMP / DICOM）

平台宣称支持 `JPG / PNG / BMP / DICOM`。已对每种格式的常见变体构造真实文件，
逐项走 `算法读图 → 上传 → 推理 → 原图回传 → 标注图` 全链路实测（共 17 个变体，全部通过）：

| 变体 | 算法读图 | 上传 | 推理 | 原图 Content-Type | 标注图 |
|---|---|---|---|---|---|
| JPG 基线 / 灰度 / 渐进式 / 低质量(q30) | ✅ | ✅ | ✅ 阳性 | image/jpeg | ✅ |
| PNG RGB / RGBA / 灰度L / 调色板P | ✅ | ✅ | ✅ 阳性 | image/png | ✅ |
| **PNG 16 位灰度 (I;16)** | ✅（已修） | ✅ | ✅ 阳性 | image/png | ✅ |
| PNG 1 位黑白 | ✅ | ✅ | 图像质量不佳 | image/png | ✅ |
| BMP 24 位 / 8 位调色板 / 32 位RGBA / 顶向下 / 灰度L | ✅ | ✅ | ✅ 阳性 | image/bmp | ✅ |
| DICOM 16 位（含前面 §2.3 的压缩与多帧变体） | ✅ | ✅ | ✅ 阳性 | **application/dicom** | ✅ |
| 极小图 24×24 | ✅ | ✅ | 图像质量不佳 | image/png | ✅ |

**本次查出并修复的两个问题**：

1. **16 位 PNG 被严重破坏（算法侧可见，已修）**
   `pipeline.load_image` 原先直接 `Image.open(...).convert("RGB")`，Pillow 对 `I;16` 是**截断**而非缩放：
   实测该图 **59.8% 的像素被压成纯白**（与"原始值 >255 的像素占比"完全一致），
   模型证据分从 **0.8992 掉到 0.0423**（仅剩 3 倍阈值，换一张图就会漏检）。
   已在 `load_image` 中对 `I / I;16* / F` 模式先做 min-max 归一化到 8 位再转 RGB
   （对 8 位图像是恒等变换，行为不变）。修复后证据分回到 **0.8992**，与正确归一化完全一致。
   > 注：模型不会被空白图骗过——纯白 0.0000、纯黑 0.0000、均匀随机噪声 0.0022。

2. **DICOM 原图回传的 Content-Type 是 `text/plain`（已修）**
   `GET /api/images/{id}` 用 `FileResponse(path)`，Starlette 依扩展名推断，`.dcm` 不在其表里 → 落到 `text/plain`。
   已改为显式传入媒体类型，实测 `.dcm → application/dicom`、`.png → image/png`、`.bmp → image/bmp`、`.jpg → image/jpeg`。
   影响面较小（前端对 DICOM 走占位图 / 标注图，不靠它渲染），但属于 API 正确性问题。

**属于设计预期、不是 bug 的两项**：
* **1 位黑白 PNG** → 判「图像质量不佳」：该格式本身已把灰阶压成两值，信息不可恢复；
* **24×24 小图** → 判「图像质量不佳」：短边低于 `MIN_SIDE = 40` 的硬门槛。

## 3. 策略与阈值

### 3.0 置信度（`confidence`）是**标定后的概率**，不是原始证据分

平台契约把 `confidence` 定义为「置信度 0~1」，前端在 `class_probabilities` 缺失时直接用它展示。
而模型内部输出的是一个**未标定的证据分**（跨模型几何平均，取值范围不受约束）——
若直接填进 `confidence`，一个"稳稳的阳性"会被显示成 `39.8%`，看着像没把握。因此这里做了一次**单调标定**：

| 判定 | `confidence` 的含义 |
|---|---|
| 肠套叠阳性 | `P(阳性 \| 证据分 ≥ s)` |
| 肠套叠阴性 | `P(阴性 \| 证据分 ≤ s)` |
| 图像质量不佳 | 固定 0.90（安全网） |

* 标定表在 **190 正 / 149 负 的留出集**上一次性拟合，估计量是**拉普拉斯平滑的阈值精度**（α=1）并做单调化，
  上下限 `[0.50, 0.999]`（不宣称 100%）；
* **决策阈值完全不受影响**——同一批 339 张复核，分类结果逐位不变
  （关安全网 183/9/7/140 → Prec 0.9531 / Acc 0.9528；开安全网 4 张转「图像质量不佳」）；
* 校验点：证据分 = 阈值 0.014451 处，标定值 0.9485 ≈ 同批实测 Precision 0.9531；
* `class_probabilities` 同步改为由标定值导出的三分类概率（此前填的是 `{score, 1-score, 0}`，不是概率）。

**全语料实测效果**（6,998 张）：`confidence < 50%` 的图片由 **350 张降为 0 张**，
其中 321 张原本是"判定正确、只是数字小"的假低置信。

### 3.0.1 默认策略：`v1r` —— 综合 v1 与 v2 的优势

仓库里有两套权重。它们各自的强项与短板是**互补**的：

* **v1**：阈值已用无偏数据标定（偏差仅 1.05），Precision 达标；但判别力较弱，
  有 7 张完全静默的真阳性。
* **v2**：判别力明显更强（阈值无关地占优，7 张静默漏检全召回、双 95% 可行带宽 4.5 倍）；
  但它的阈值没有无偏来源，直接全局启用会让 Precision 掉到 0.9307（<95%）。

**因此默认策略改为 `v1r`：用 v1 做判定锚点，只在 v1 判定为阴性且"证据分非零"时，用 v2 做保守补救。**

```
阳性  ⟺  v1 ≥ 0.014451                                    （主判定，阈值已标定）
      或  ( v1 > 0  且  v2 ≥ 0.182090 )                    （补救分支）
                              ↑ dev 负样本 99 分位（纯 dev 口径，未使用留出集）
```

339 张留出集实测（三项同时变好）：

| 策略 | TP | FP | FN | TN | Precision | Accuracy | Sensitivity |
|---|---|---|---|---|---|---|---|
| `v1`（旧默认） | 183 | 9 | 7 | 140 | 0.9531 | 0.9528 | 0.9632 |
| **`v1r`（现默认）** | **184** | 9 | **6** | 140 | **0.9534** | **0.9558** | **0.9684** |
| `v1r` + 安全网（部署口径） | 184 | 9 | 2 | 140 | 0.9534 | **0.9672** | 0.9684 |
| `v2` 全局启用（对照，未标定） | 188 | 14 | 2 | 135 | 0.9307 ❌ | 0.9528 | 0.9895 |

**为什么是这两个条件**（换了就不是最优）：

* **`v1 > 0` 是关键**：补救要救的 `图片 (124)` 的 v1 分数是 **0.0036（微弱但非零）**，
  而被 v2 误报的阴性其 v1 **恰好为 0.0000** —— 这就是可分性的来源。
* 若放宽到"v1 可以为 0"，能救更多（TP 186）但 FP 升到 12–14、Precision 掉到 0.93–0.94，
  **不满足 95% 硬门槛**，因此不做。剩下 6 张静默漏检的 v1 分数都恰好是 0，今天在门槛内救不回来。
* τ2 的**可用窗口宽 0.135–0.247**（不是刀尖上的点）；取 dev 负样本 99 分位落在窗口内。
* 成本：补救分支在 dev 负样本上触发 **0.89%**、在 149 张留出负样本上**新增假阳 0 张**；
  长期期望约 1% 的阴性会被多判为阳性。

**性能**：补救条件是 `v1 > 0`，所以 **v1 恰好为 0 时无需跑补救模型** —— 实测 86.6% 的阴性图
其 v1 分数正是 0，这些请求仍只跑 2 个模型。整体平均耗时 0.93 s → **1.47 s**（+57%），
触发补救的请求约 4–7 s，仍远低于前端 30 s 超时。

**如何切换回纯 v1**（一行）：把 `model_core.POLICY` 改成 `"v1"`。
补救分支与阈值都在 `POLICIES["v1r"]` 里，可单独调 `rescue_threshold`。

### 3.0.2 备选：把 `v2` 全局启用（需先标定阈值，当前被硬护栏挡住）

`v2` 的判别力更强（阈值无关地占优），但它的阈值没有无偏来源。同一批 339 张留出集实测：

| | **v1** | **v2** |
|---|---|---|
| 阈值 | 0.014451（已用无偏数据标定，偏差仅 1.05） | 0.031078（沿用 v1 同一常量，**未标定**） |
| TP / FP / FN / TN | 183 / 9 / 7 / 140 | 188 / 14 / **2** / 135 |
| **Precision** | **0.9531** ✅ | **0.9307** ❌ |
| Accuracy | 0.9528 | 0.9528 |
| Sensitivity | 0.9632 | **0.9895** |
| ROC-AUC | 0.9772 | **0.9946** |
| 双 95% 可行带宽 | 0.0050 | **0.0225** |
| 每次请求模型数 / 端到端耗时 | 2 个 / 1–2.5 s | 8 个 / 4–7 s |

**阈值无关地看，v2 确实更强**（相同假阳数下的真阳数，满分 190）：

| 假阳数 FP = | 0 | 2 | 4 | 6 | 8 |
|---|---|---|---|---|---|
| v1 | 133 | 170 | 171 | 180 | 183 |
| **v2** | **164** | **178** | **182** | **182** | 183 |

也就是说：**v2 是更好的模型，但它现在还差一个阈值**。在未标定的阈值下启用它，
Precision 会掉到 0.9307，**不满足既定的 Precision ≥ 95% 硬门槛**，因此不能作为默认值。

**v2 转正的唯一条件与步骤**（无需重训、无需 GPU）：

```powershell
cd backend
python -m algorithm.backfill_shadow            # 1. 对已存盘影像批量采集候选策略分数（零延迟影响）
python -m algorithm.calibrate_shadow --export  # 2. 出标注清单 + 复核页
#    ← 人工/临床填 shadow_data/labels.csv 的 label 列
python -m algorithm.calibrate_shadow --fit     # 3. 在无偏样本上拟合阈值并给出 go/no-go
# 判定通过后按提示改三处：
#   POLICIES["v2"]["threshold"] = <拟合值>
#   V2_THRESHOLD_CALIBRATED = True
#   POLICY = "v2"
```

在标定完成之前，`model_core` 用 `V2_THRESHOLD_CALIBRATED = False` **硬性挡住** v2，
直接启用会抛出明确错误而不是静默给出低精度结果。

> 若业务上更看重"尽量不漏"而非 95% 的精度下限，可以把默认切成 v2 —— 但那是**产品决策**，
> 需要同时接受 Precision 0.9307 / 假阳翻倍 / 推理耗时翻 3–4 倍，请明确确认后再改。

### 3.1 默认策略 `v1`（现部署）

```
委员会 : intussusception-obb-v1-large.pt + intussusception-obb-v1-compact.pt       恰好 2 个模型
门控   : quorum=1，跨模型一致所需 OBB IoU ≥ 0.05
多尺度 : 640 首推；某模型 640 最高 conf < 0.20 才复推 1280
候选   : conf ≥ 0.001，每模型取 top-3
融合   : geo = sqrt(v_11s × v_11n)，两个成员都必须给出有效值，否则记 0
判定   : score ≥ 0.014451 → 肠套叠阳性；否则 肠套叠阴性
```

阈值来源：dev 负样本（450 张 `normal/`）的 94.3 分位。**该阈值可直接部署**——它对留出负样本的
标定偏差因子仅 **1.05**（本地实测）。

339 张 Final Test 实测：**TP=183 FP=9 FN=7 TN=140 → Precision 0.9531 / Accuracy 0.9528 /
Sensitivity 0.9632 / ROC-AUC 0.9772**；双 95% 可行 TARGET_FPR 带 [0.0550, 0.0600]。

### 3.2 实验策略 `v2`（**默认被硬性护栏挡住，勿用于临床**）

由 4 对同类模型取均值融合。它的**判别力更好**：
AUC 0.9946（vs 0.9772）、7 张原本完全静默的漏检 **7/7 救回**、可行带 0.0050 → **0.0230**。

但它的**阈值尚未在 out-of-fold 数据上重锁**：dev 负样本被用于训练（样本内），标定偏差因子达 **1.63**，
直接沿用同一常量会让 Precision 掉到 **0.9307（<95%）**。因此：

```python
# model_core.py
V2_THRESHOLD_CALIBRATED = False   # 未重锁前，启用 v2 会直接抛错
```

用无偏数据把阈值标定好之后，把该开关置 True 并更新 `POLICIES["v2"]["threshold"]` 即可切换（代码路径已就绪）。

### 3.3 安全网（`SAFETY_NET = True`）

```
score == 0 且 黑像素占比 > 0.70  →  返回「图像质量不佳」（建议提高增益/更换切面复扫）
                                 而不是「肠套叠阴性」
```

* **收益**：190 张阳性里 6 张整图完全无响应，其中 **4 张**（`图片 (18)(54)(58)(59)`）被该规则覆盖，
  不再被报成"阴性"；
* **代价**：独立 dev 负样本 450 张上误触发 10 张 = **2.2%** 的阴性会被要求复扫
  （test 上 0/149 属同分布下的幸运抽样，**以 2.2% 为准**）；
* **定位**：**启发式安全网，不是统计判定**。可开关、可随证据更新。

## 4. 已排除的方向（避免重复走）

| 方向 | 结论 |
|---|---|
| 提高推理分辨率（1536/2048） | 不改变病灶相对尺度，多次证伪 |
| 裁黑边 / 裁超声扇区 | 全测试集外接框保留率 p05=0.92，没有可裁的黑边 |
| 推理侧切片 / 中心裁剪 / 弱响应引导复判 | **两种不同设计同型失败**：阈值被负样本抬到 0.81，AUC 0.9772→0.9455 |
| 光度/增益归一化（CLAHE、百分位拉伸、Gamma） | 对 7 张漏检**分数仍是 0.000**，只有几何裁剪才点亮 |
| 亚型平衡负样本过采样、分辨率条件阈值 | dev 与 final 给出相反排序 / 标定方向错误 |
| 跨 run / 跨配方委员会 | 完整枚举后无优势；基线本就是 28 个两委员会里的第 2 名 |

根因结论：模型学到的是 **「紧裁剪 ⇒ 阳性」的捷径**（正样本全是紧贴病灶的裁剪、负样本全是宽帧）。
v2 的"对称取景随机化"正是针对这一点，因此才有效（6/7 静默漏检被救回）。

## 8. 影子数据与阈值标定（为切换 v2 铺路，**零 GPU、零延迟影响**）

v2 的判别力更好但阈值没有合法来源（见 §3.2）。**推荐的解法是影子标定**，而不是再跑 10h CV
（后者已做过本地预验证并否定）。

### 8.0 影子数据是什么

**定义**：让**候选策略（v2）对每张真实影像"顺手算一遍分数、但结果不参与诊断"**，
把这份分数与影像存下来。它像影子一样跟着主流程跑，不影响任何判定 —— 所以叫"影子数据"。

**为什么必须要它**：标定阈值必须在**无偏**负样本上做，而：

| 候选来源 | 为什么不能用 |
|---|---|
| 训练用过的 450 张负样本 | 模型见过（v2 还对它们做过重取景）→ 分数被系统性压低 → 定出的阈值偏低 → 真实 Precision 只有 0.9307 |
| 留出的 149 张测试负样本 | 是**评测基准**，拿它标定等于测试集调参 |
| 交叉验证折外分数（OOF） | 已预验证并**否证**：留出半集上双 95 达成率仅 50–53%，规则在 300 例量级是负收益 |

**只剩一条路**：等**部署后新到的、模型没见过、也没用于评测的真实影像**。这就是影子数据。

**存什么**：

```
shadow_data/
├── shadow.jsonl     每行一条：时间 / md5 / 尺寸 / 黑占比 / 主策略分数与判定 / 候选策略 v2 分数
├── images/<md5>.jpg 影像副本（按 md5 去重，同一张只存一份）
├── labels.csv       人工标注（1=阳性 / 0=阴性）
└── review.html      浏览器逐张复核页
```

**⚠️ 三条硬约束（前两条已内建为护栏）**：

1. **必须是模型没见过、且未用于评测的影像** —— 脚本按**图像内容 md5 + 近似重复**双重比对，
   排除训练语料与留出测试集（默认排除清单约 8,000 张：4 个标注目录 + `normal/` + `test190_new`），
   命中即跳过并打印计数与原因。
   > `normal/` 也整目录排除：599 张里有 450 张被用作训练负样本（约 75% 受污染），
   > 而按 md5 无法区分哪些是训练用的 —— **宁可少采，不可采脏**。
   >
   > 近似重复比对（16×16 灰度描述子，平均绝对差 ≤0.0020）是必需的补充：实测同一张图
   > **只改 JPEG 质量**，像素平均差仅 0.685/255、而内容 md5 已经变了，精确比对拦不住。
2. 标注必须来自**人工/临床**，不能拿模型分数当标签（否则是循环论证）；
3. 拟合前工具要求**阳性 ≥120 且阴性 ≥120**。

**自动采集**：`python -m algorithm.shadow_daemon`（独立进程，每 10 分钟扫一遍 `uploads/`，
离线补算、不影响线上延迟；`--once` 可挂计划任务）。真实影像一进来就开始积累，
不需要人记得跑脚本。

> 因此：**平台 `uploads/` 里已有的影像不能直接用来标定** —— 我们测试时上传的都取自语料/测试集，
> 会被护栏剔除。真正可用的数据只能来自**部署后新上传的临床影像**。

### 8.1 为什么不用"请求内实时影子"

`shadow.SHADOW_ENABLED=True` 虽然只入队不阻塞，但后台 v2 融合推理 = **8 个模型**，会和请求抢 CPU。
本地 A/B 实测（Ryzen 7 5700U，CPU 推理）：

| 配置 | 请求中位耗时 |
|---|---|
| 影子关闭 | 1057 ms |
| 影子开启（不限速） | 2217 ms（**拖慢 2.1×**） |
| 影子开启（限速 3/min） | 2296 ms（仍 +1156 ms） |

→ 限速只降频率、不降单次争用。**因此 `SHADOW_ENABLED` 默认 False。**

### 8.2 推荐方式：批量回填（对已存盘影像）

```powershell
cd backend
# 回填平台已上传的全部影像（默认取 config.UPLOAD_DIR）
D:\Program\miniconda3\envs\detect\python.exe -m algorithm.backfill_shadow
# 限量试跑 / 指定目录 / 已知整批为阴性时顺手打标
D:\Program\miniconda3\envs\detect\python.exe -m algorithm.backfill_shadow --images D:\normal --assume-label 0
# 看进度
D:\Program\miniconda3\envs\detect\python.exe -m algorithm.backfill_shadow --status
```

* 写入 `algorithm/shadow_data/shadow.jsonl`，按图像 md5 去重、**可中断续跑**（实测二次运行 0 新增 / 8 跳过）；
* 图像存一份到 `shadow_data/images/<md5>.jpg` 便于复核；关掉 `SHADOW_SAVE_IMAGES` 则不存；
* 建议用 Windows 计划任务 / cron **每晚跑一次**。实测约 **4.2 s/张**（8 模型）。

### 8.3 标定与判定

```powershell
D:\Program\miniconda3\envs\detect\python.exe -m algorithm.calibrate_shadow --export   # 出 labels.csv + review.html
#   ← 人工/临床填 label 列（1=阳性，0=阴性）
D:\Program\miniconda3\envs\detect\python.exe -m algorithm.calibrate_shadow --fit
```

判定逻辑（对应 p27 的教训）：

* **不取边界点** —— 取"Prec≥0.95 且 Acc≥0.95"的**可行阈值区间中点**，并要求区间宽度 ≥0.010；
* **给出同数据上部署策略的对照**（含 bootstrap 5% 下界），避免"换了数据才好"的错觉；
* 默认 **`--mode relative`（相对占优）**：点估计均 ≥0.95 **且**同批数据上（点估计与 5% 下界）都不劣于 v1
  且可行区间够宽 → 建议切换；
* `--mode strict`（绝对 5% 下界 ≥0.95）在小样本下**谁都过不了**——实测在 339 张上
  现部署策略的下界也只有 Prec 0.9293 / Acc 0.9323；要把 Acc 下界抬到 0.95 需 n≈3459。
  该模式仅在你确需绝对保证且样本足够时使用。
* 门槛：默认阳性 ≥120 且阴性 ≥120 才拟合（`MIN_POS/MIN_NEG`）。

判定通过后按提示改三处即可切换：`POLICIES["v2"]["threshold"]`、`V2_THRESHOLD_CALIBRATED=True`、
`POLICY="v2"`，然后重跑 `eval_algorithm.py` 复核。

> 影子样本是**真正无偏**的（模型从没见过它们），比交叉验证的折外分数更干净，且不需要任何 GPU。

## 9. 必须随结果一起理解的边界

1. **同配方只换随机种子，Accuracy 摆动 ±3.5pp**（4 个种子）。v1 是其中最好的一次；
   0.9528 是**点估计**，不代表该配方的稳定水平。
2. **v1 的双 95% 只对 73% 的负样本 bootstrap 重采样成立**（融合为 99%）→ 应表述为"点估计 + 区间"。
3. **6/190 的阳性在整图推理下完全无响应**（`enema_failure` 低增益小病灶）；其中 4 张由安全网兜住，
   另 2 张（`图片 (20)(124)`）仍无法覆盖。
4. **评估集存在来源混淆**：190 张正样本 100% 是 `图片 (n)` 命名，149 张负样本 0% 是它 →
   绝对指标应视为**上界**。
5. `severity` / `treatment_success_rate` 一律留空：本项目没有经过验证的对应模型，不编造数值。
